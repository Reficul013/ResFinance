# ResVault Pinned-Source Audit

Date: 2026-10-12

Audited source: Apache ResilientDB commit `4de5cb43686276ace4307f44839a1de920ab524a`

ResVault manifest version: 1.2.2

Decision: Official upstream cannot be used unchanged; substantial hardening is required.

## Findings

### Critical — decrypted private key crosses into the webpage

[`public/background.js`](https://github.com/apache/incubator-resilientdb/blob/4de5cb43686276ace4307f44839a1de920ab524a/ecosystem/tools/resvault/public/background.js#L514-L544) handles `getSigningKeys` by decrypting and returning both the private and public key. [`public/content.js`](https://github.com/apache/incubator-resilientdb/blob/4de5cb43686276ace4307f44839a1de920ab524a/ecosystem/tools/resvault/public/content.js#L512-L537) then posts `response.privateKey` to the page with `window.postMessage`. Any page script on the connected origin can receive the signing seed. This directly violates the rule that private keys never leave the extension.

Required change: accept a canonical intent in the background context, present the approval UI from an extension-owned surface, sign internally, and return only the public key/address/signature/result.

### High — encryption key is exportable and stored beside ciphertext

The [background storage path](https://github.com/apache/incubator-resilientdb/blob/4de5cb43686276ace4307f44839a1de920ab524a/ecosystem/tools/resvault/public/background.js#L331-L371) generates an extractable AES-GCM key, exports it as JWK, and stores the exported key in the same local record as the encrypted private key. This protects against accidental plaintext inspection but does not create meaningful separation if extension storage is read.

Required change: derive a non-exportable key-encryption key from the password with Argon2id, persist only versioned salt/parameters/ciphertext/nonce, and keep derived and decrypted key material memory-only while unlocked.

### High — raw password is persisted

[`src/pages/Login.jsx`](https://github.com/apache/incubator-resilientdb/blob/4de5cb43686276ace4307f44839a1de920ab524a/ecosystem/tools/resvault/src/pages/Login.jsx#L121-L124) writes the login password to `chrome.storage.local`. The context later reloads it and uses it for key operations.

Required change: never persist the raw password; keep unlock state in the extension background memory with inactivity and lifecycle locking.

### High — overly broad page bridge

The [manifest](https://github.com/apache/incubator-resilientdb/blob/4de5cb43686276ace4307f44839a1de920ab524a/ecosystem/tools/resvault/public/manifest.json) injects the content script into `<all_urls>`, and the page listener accepts messages without a configured application-origin allowlist. Responses are posted with target origin `*`.

Required change: restrict host permissions and runtime origin checks to explicitly configured ResFinance origins, validate message schemas and request IDs, and post only to the exact requesting origin.

### Medium — duplicate key stores and legacy password construction

The UI keeps multiple encrypted representations of private material in sync storage and local storage and uses CryptoJS password-based encryption without a documented Argon2id policy. This increases state and migration risk.

Required change: define one versioned encrypted-seed record, one migration path, and tests for lock, import, rotation, corruption, and deletion.

## Disposition

The combined issues cross the background/content/page boundary and change storage/unlock architecture. They exceed a one-line compatibility patch, so ADR 0001 selects the substantial-hardening path. ResVault remains in scope; the work moves to Milestone 2 after the Milestone 0 contract and tests are complete.

## Required acceptance tests

- Page scripts never receive seed, private key, password, or derived key.
- Network and backend captures contain only approved intent data, public identity, and signature.
- Signing is rejected while locked and after timeout/restart until explicit unlock.
- Wrong origin, audience, network, resource, nonce, expiry, and parameter hash are rejected.
- Approval UI displays the exact action and material parameters.
- Storage inspection finds only the versioned encrypted-seed record and public metadata.
- Logs and errors remain secret-free under success and failure paths.
